# LAN Party rewrite plan

Goal: rebuild LAN Party as a small Go/Fyne Linux app that publishes chosen
TCP and UDP ports over one encrypted QUIC tunnel, with one-time invites,
device approval and a fixed 400×600 interface.

Architecture: a host app listens on one UDP port and authenticates friends by
device key. A friend app opens loopback listeners for the services the host
published and carries each connection over a QUIC stream or datagram. The host
dials fixed LAN targets. No virtual network, no gVisor, no WireGuard.

Tech stack: Go 1.27.4, Fyne 2.8.2, quic-go, zalando/go-keyring, Linux only
for this version.

Design: `docs/design.md`.

Execution: native in this session, one task at a time. Each task ends with a
green test run and a commit.

## Global constraints

- Go 1.27.4 from `.tools/go`; `GOCACHE`, `GOMODCACHE`, `GOPATH`, `TMPDIR` and
  the XDG directories point inside the project during development.
- Fyne 2.8.2. No webview, no npm, no Electron.
- Window fixed at 400×600. No resize, no maximise.
- Linux only. Windows is a later branch of work.
- Runtime files: `~/.config/lan-party/settings.json` and
  `~/.local/share/lan-party/groups.json`, both 0600 in 0700 directories.
- Private keys live in the OS keyring. Invite tokens are stored only as
  SHA-256 hashes. No secret in JSON, invites or logs.
- Friend listeners bind `127.0.0.1` only. The host binds one UDP port.
- Sentence case copy. No emoji, gradients, glows or invented status.
- Commit messages are past tense and explain the change.
- `make test` must be green before every commit.

## Review focus

These are the failure modes the design implies but no single test may make
obvious. Each one gets a test in the task that owns the code.

1. **A used, expired or revoked invite must never open a connection.** Test in
   tasks 3, 4 and 8.
2. **A different device key for a known member must require approval, not
   silently replace or reject without explanation.** Test in task 8.
3. **A target with a wildcard, a multicast address or an ambiguous port remap
   must be rejected.** Test in task 3.
4. **A friend-side port already in use must fall back to the next free port and
   show the real one, not fail silently.** Test in task 6.
5. **A peer must not exhaust the host with streams, flows or enrollments.**
   Test in tasks 5 and 7.

- [ ] **Step 3: Implement TLS and the server**

ALPN `lanparty/1`. Server TLS: host certificate, `MinVersion TLS 1.3`,
`ClientAuth: tls.RequireAnyClientCert`. Client TLS: `InsecureSkipVerify` plus a
`VerifyConnection` that compares `secure.Pin` with the configured pin. Server
QUIC: `MaxIdleTimeout 30s`, `KeepAlivePeriod 10s`, `EnableDatagrams true`,
`MaxIncomingStreams 128`. Accept loop: for each QUIC connection, handshake in a
goroutine, open the control stream, read `hello`, call `Authenticate`, send
`welcome` or `denied`, then deliver the `*Conn` on an internal channel.
`Server.Accept` reads that channel.

- [ ] **Step 4: Implement the client and control stream**

`welcome` or `denied`, and returns. The control reader decodes consecutive JSON
values into a buffered channel. A mutex serializes writes. `Ping`/`Pong` are
left to the caller; the tunnel only carries them.

- [ ] **Step 5: Implement data streams and datagrams**

The first client-opened stream is control. Data streams carry a newline-
terminated JSON `DataHeader` followed by raw bytes. `OpenData` writes the
header, flushes and returns the stream. `AcceptData` reads the header and
returns the stream. Datagrams are raw payloads; the forward layer adds its own
flow id.
